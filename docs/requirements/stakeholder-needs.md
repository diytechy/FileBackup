# Stakeholder Needs (SN-###)

Owned by the **Stakeholder** hat — whoever the system serves (here: the owner
running his own backups). Plain-language needs + edge-case expectations.
Engineering translations live in `system-requirements.csv` (referenced by
`SN-Refs`); do not restate them here. Priority: **M**=Must · **S**=Should ·
**C**=Could.

## Core needs

| SN-ID | Need (plain language) | Why it matters | Priority | Acceptance intent (how we'd know it's met) |
|---|---|---|---|---|
| SN-001 | Back up an entire source tree, periodically, capturing every file. | The whole point — nothing in the source may be silently skipped. | M | Run against a known tree; every source file appears in the backup's index; re-running picks up new and changed files. |
| SN-002 | Don't waste space storing identical content twice. | Large media trees have many duplicate files; storing each once saves real disk. | M | Two files with identical bytes occupy the space of one stored copy, and both restore byte-exact. |
| SN-003 | Optionally compress stored data to save more space. | Compressible documents/text shrink a lot; already-compressed media shouldn't be re-packed. | S | With compression on, content that measurably shrinks is stored compressed and content that does not is stored as-is, whatever the file's name; with compression off nothing is compressed; every file restores byte-exact either way. |
| SN-004 | Keep point-in-time snapshots of earlier states, each fully restorable. | Lets me recover an older copy after an accidental edit/delete — and trust that restoring "as of date X" reproduces exactly what existed then. | M | After several runs, each earlier backed-up state can be picked by its date, and restoring it reproduces that exact state (changed files at their old content); the latest state is always restorable. |
| SN-005 | Restore the original tree **bit-for-bit from the backup folder alone**, without installing FileBackup and using only commonly available tools. | A backup I can't restore on a clean machine is worthless. | M | Copy a backup folder to a machine without FileBackup, run its restore kit using only commonly available tools, and byte-compare the result to the original: identical. |
| SN-006 | Restore a *historical* snapshot, not just the latest. | I may want the state as of a specific earlier run, picked by date. | S | Running the restore kit inside a specific dated snapshot folder rebuilds exactly that earlier state, byte-for-byte; running it from the backup root rebuilds the latest state. |
| SN-007 | Control how often unchanged files have their content rechecked, to trade speed against integrity. | Rechecking a huge tree every run is slow; I want options from every run to never. | S | Each recheck setting, from every run to never, decides deterministically whether an unchanged file's content is rechecked on a given run. |
| SN-008 | See what is in the backup and find a file by name, without running a restore. | The store is organised by content rather than by the original folder tree, so it cannot be browsed directly; a listing generated from the index is the one way to see and find files without restoring, and it can be more faithful than a mirrored copy because it lists every path, duplicates included. | S | The generated index lists every logical path — including every duplicate sibling — and opening an entry opens that file's stored object. |
| SN-009 | Back up several independent source/target sets from one config and one run. | I have multiple data roots; one scheduled job should cover them. | S | A config with multiple `BackupSets` processes each independently in one invocation. |
| SN-010 | Optionally email me whether the backup succeeded or failed. | For unattended/scheduled runs I want to know without checking logs. | C | With SMTP configured, a success/failure email arrives; with it omitted or `-NoMail`, none is sent. |
| SN-011 | Run unattended/scheduled without ever blocking, with a clear pass/fail signal. | A scheduled task that hangs on a prompt or hides failures is dangerous. | M | A scheduled run completes without prompting and returns exit 0 on success, non-zero if any set failed. |
| SN-012 | Get set up on the first run with discoverable docs and a config builder. | New users (and future me) shouldn't have to reverse-engineer the config. | S | The shipped quick-start documentation and the configuration builder let a new user build a config and run a first backup; required dependencies install on first use. |
| SN-022 | Restore a backup on a **Linux** machine from the backup folder alone, without the runtime the backup tool itself needs. | The restore host is often not Windows (NAS, rescue live-USB, a borrowed laptop); the backup must not be hostage to one runtime. | S | Copy a backup folder to a stock Linux machine carrying only the documented, commonly available tools, run the backup's own POSIX restorer, and byte-compare: identical tree, from the backup root (latest) or any dated snapshot (that point in time); failures exit non-zero. |
| SN-023 | Produce backups **from a Linux host** interoperable with the Windows implementation. | Lets Linux machines run the same scheduled backups against the same targets; either side can restore what the other wrote. | C | A backup made by the Linux backup engine restores byte-exact via either restorer, and vice versa; dedup/snapshot semantics match the shared contract. |
| SN-024 | Run backups in a Linux container without installing the backup runtime on the backup host. | The backup host can run the backup engine without a host runtime installation. | M | The container produces a compressed backup that restores byte-exact. |
| SN-026 | When a restore fails, a script (and I) can tell *what kind* of failure it was without reading the log. | A wrapper (a backup host's supervisor, a scheduled task) has to decide between "your bytes are gone", "fix this host and retry", and "you pointed me at the wrong folder" — one generic failure forces a human into the log every time. | S | Both restorers return the same documented exit code per failure class; deliberately induced instances of each class (clean, content missing, host/dependency problem, bad invocation/precondition, damaged index) each return their own code, identical on Windows and Linux. |
| SN-029 | Remove old snapshots to bound backup growth, **without ever destroying content a surviving snapshot still needs** — and be told, before removing anything, what each removal would actually reclaim. | Without a way to remove snapshots, retention is unbounded and the backup volume eventually fills. But snapshots share bytes: a folder that looks like old history can hold the only physical copy of content other snapshots recover by hash, so deleting it from outside the tool is silent data loss. Whoever decides *what* to keep needs the tool to do the *removing* — and needs real reclaim numbers, which only the tool can compute because of dedup. | M | Asking the tool to remove a named snapshot leaves every remaining dated state — and the latest state — restorable byte-exact with compression on or off, including when the removed folder held the only copy of shared content; a dry run first reports the same reclaim figure the real removal achieves; anything that would lose content is refused before a single byte is touched, with a distinct exit status; a run interrupted at any point loses nothing and can simply be run again. |
| SN-030 | Trust that what is actually stored matches what the index says about it — and that turning compression on or off, or changing the compression policy, never quietly damages an older snapshot's restore. | The index records how each file was stored (compressed or not) apart from the bytes themselves; unless something checks that record against the bytes on disk, a wrong entry validates itself forever and a restore can write archive bytes under the original filename and report success. Changing the compression policy leaves a store holding both forms, which is ordinary use, so the hazard is reachable without any tampering. I also need to be told before a backup starts that the destination has room, the way a restore already tells me. | M | An on-demand check reports every place the stored form and the index disagree, across the live backup and every snapshot, without changing anything, and a repair mode fixes the ones that are unambiguously wrong; restoring any state after a compression-policy change reproduces the original bytes exactly, or fails loudly, but never writes archive bytes under a real filename; a backup run that would not fit refuses before writing anything. |
| SN-031 | If something outside the tool damages the backup store — antivirus quarantine, a cloud-sync "free up space" sweep, someone tidying a folder that looks like an ordinary copy — the next backup run should put it right while the source still can, and the verification action should tell me about anything it cannot put right. | The backup root looks like a plain copy but is a managed, deduplicated pool. If a lost data file were only blanked out of the index, every later run would report success forever: the entry would never be re-copied although the source still holds the bytes, a new file with the same content could silently inherit the broken entry, and the verification action would report the store clean. | M | After a data file inside the backup root is externally deleted: the next backup run exits 0 having re-established that file's bytes from the still-matching source, and the restored tree is byte-exact; a new source file with identical content never adopts an index entry that no longer points at stored bytes; the verification action reports every entry whose bytes are gone from the backup entirely, with a distinct finding class and non-zero exit, instead of reporting the store clean. |
| SN-032 | A file whose name cannot exist on both Windows and Linux should be refused loudly at backup time — not half-handled. | The two restorers must stay interchangeable over the same store (SN-022/SN-026). Names with quotes or newlines are legal on Linux but break the cross-platform tooling contract (the archive tool's argument quoting, the POSIX restorer's index parsing), and names with `\` mean different things on each side. Handling every such case is complexity spent on names the user almost certainly wants fixed at the source anyway. | S | A source file whose name is invalid on either platform is skipped with one ERROR naming the file and the offending character, the set fails (non-zero exit), everything else in the set is still backed up, and no index entry is written for the skipped file. |
| SN-033 | A restore that reports success has **proved** the bytes it wrote against the index. | Without a check of the written bytes, a wrong payload, a same-length bit-flip or even a truncated stored file would all restore with a success status. A backup whose restore can silently hand back damaged bytes and still say "done" is not a backup. | M | A store whose data file has been altered (wrong payload, bit-flip, or truncation) restores byte-exact from another surviving copy in the backup, or fails non-zero naming the file — never exit 0 with wrong bytes. |
| SN-034 | Nothing already stored in the backup may be silently rewritten by a later run. | When files share stored content, an ordinary edit of one of them must not overwrite the shared stored copy in place: that would orphan every other file still claiming those bytes, invisibly to every default check and discoverable only after the fact. A store that quietly loses the last copy of content it reported as backed up is not a backup. | M | After editing one of two identical files, restoring the previous snapshot still reproduces the old bytes for **both** paths, and the store's audit reports no index entry whose content is unaccounted for; no stored bytes ever change while the current index still claims them. |
| SN-035 | Start a restore without recalling a command, and restore on a **Mac**. | The moment I need a restore is the worst possible moment to have to remember a parameter name, so a restore must start from a double-click and keep its outcome on screen long enough to read. And the restore host is often a borrowed laptop, which may be a Mac: a restorer that misreads a non-GNU userland and reports damage on an intact backup is worse than one that refuses to run. | S | Double-clicking the launcher on Windows or macOS opens a normal folder dialog, restores, and leaves the result on screen; a scripted call is unaffected and still returns its exit code. A machine with BSD rather than GNU coreutils, meeting the documented tool floor, restores byte-exact - or fails loudly naming what to install - but never reports damage that is not there. |
| SN-036 | A restored tree should come back the way it was, not merely with the right bytes: every file carrying its own modification time, my empty folders present, and a folder I made hidden still hidden. | Dedup stores identical files once, so unless each file's own modification time is applied, every twin comes back with the time of whichever file was stored first; and an index with one entry per file cannot by itself recreate an empty directory or bring back a Hidden or System folder as it was. | S | Two identical files with different modification times restore with their OWN times, with compression on or off and through both restorers; an empty directory and a nested empty directory are recreated; a Hidden+System folder comes back Hidden+System on Windows, and on Linux the directory is created with the inapplicable attributes reported rather than silently dropped; a backup written without this record still restores exactly as it did before. |

## Edge-case expectations

How the system should behave when things go wrong (the highest-value part — be
specific; the System Engineer turns each into measurable SRs).

| SN-ID | Scenario | Expected behavior |
|---|---|---|
| SN-013 | Interruption / power loss / killed mid-operation | An interrupted run never leaves a half-written state that a later run proceeds on: the next run either recovers the interrupted run's staging by itself, when it can prove from the disk alone that the interrupted run is dead and that nothing would be lost, or refuses with a clear message naming what it found; a dated snapshot only ever appears complete. |
| SN-014 | Invalid input — config file missing | Fail immediately with a clear "config not found" message and a non-zero exit; do nothing destructive. |
| SN-015 | Missing **required** dependency / wrong runtime (an unsupported runtime version, or the hashing library absent) | Fail loudly with remediation guidance; never run hashing against a bogus/absent library. |
| SN-016 | Missing external tool (the archive tool when compression is selected, the media-probe tool for media metrics) | Fail before backup mutation when a selected storage feature cannot be honored; degrade only optional media metrics, with a clear log message. |
| SN-017 | Awkward file names (Unicode, `[brackets]`, `(parens)`, spaces) | Backed up and restored correctly; path handling never mis-parses bracketed/Unicode names. |
| SN-018 | A *nested* user file happens to be named like infrastructure (e.g. the same name as the backup's index) | Treated as real user data and preserved — only true root-level infrastructure files are filtered. |
| SN-019 | Restore target too small / unwritable | The restore surfaces an insufficient-capacity/space problem (accounting for compressed data) rather than silently producing a partial tree. |
| SN-020 | Email/SMTP failure during notification | Logged as a warning; the backup itself still reports its real success/failure — mail is never load-bearing. |
| SN-021 | A run with nothing changed (idempotent re-run) | Produces an identical index and no spurious "changes"; output is deterministic across identical re-runs. |
| SN-025 | The backup's index itself is damaged — truncated, partially written, or replaced by an unrelated/garbage file | The restore refuses to run rather than "succeeding" against a shrunken job, and refuses before restoring anything; this holds for the latest state and for every dated snapshot, through both restorers. A backup written before its index could be proved still restores, with a clearly logged "unverified index" warning. |
| SN-027 | The configuration file is wrong — a mistyped key, a quoted `"false"` where a boolean belongs, a missing required field, or a file written for a different version of FileBackup | The run refuses to start and says exactly which key is wrong and what was expected, before touching any backup data; it never guesses a default for a key it does not recognize, and a config written for a newer FileBackup is refused by name rather than half-understood. The JSON form is the documented, versioned contract and the shipped example configuration is itself valid; the older CLIXML form keeps working as a native-Windows convenience. |
