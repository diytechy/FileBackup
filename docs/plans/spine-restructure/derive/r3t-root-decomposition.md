# Round 3t: the top-level decomposition pass (unattended, session 2026-10-18 e)

The Owner asked for the decomposition to be finished unattended, by best
judgement, with every call that deserves a closer look recorded for review.
Those calls are collected in [../../../../DECOMPOSITION-REVIEW.md](../../../../DECOMPOSITION-REVIEW.md)
at the repo root. This record is the working: the top-level scope gets the
same pass the backup engine and the restore kit had in round 3o (states,
boundaries, an N2 chart, the sibling argument and the descend test), using
ai-template's ruled method (review-churn item 12) and the architecture
research's additions
([../architecture-breakdown-research.md](../architecture-breakdown-research.md):
Parnas goal (g), the N2 chart, correspondence between flows and structure).

Applied by `r3-merged/_r3t_apply.py` and `r3-merged/_r3t2_apply.py`. Checked by
[../check_design_layer.py](../check_design_layer.py), committed with this record.

## States at the top level

Flow 0 in [../../../runtime-flows.md](../../../runtime-flows.md): started,
admitted (every location set validated, dependencies resolved once), running
(each location dispatched in turn, whatever the last one's value), folded,
notified; refused as the early ending. The backup's own modes are flow 1 and
the restore's flow 5.

## What the pass found and changed

| Found | Change | Why |
|---|---|---|
| The launch dispatched every operation and folded its value through no interface row (the flows showed "take the claim", "refused 2" and the findings going back to it). | New internal **IF-048 Location operation request and result** (owner CMP-002; consumers the operation components). LLR-014 (run each location, fold the values) now constrains it. | The biggest internal boundary in the system; one form for every operation's answer is what makes the fold and the never-prompt rule decidable in one place. |
| The change set passed from source scan to publication unnamed. | New internal **IF-049 Change set** (owner CMP-009; consumer CMP-011). LLR-113 now constrains it. | A narrow value between two decisions (how change is judged, and how a state is published). The Owner kept the two components apart (Calls 1 and 2), so the value between them is an interface. |
| Entry results passed from entry restoration to the outcome unnamed. | New internal **IF-050 Entry results** (owner CMP-019; consumer CMP-021). LLR-056 now constrains it, placing it on entry restoration. | The restore's one value is decided from these results alone, on every route. |
| The tools resolved at launch reached every operation unnamed. | New internal **IF-051 Resolved dependencies** (owner CMP-004) and a new child **LLR-164** (under LLR-020): resolved once per launch, used by every location. | Neither existing provisioning row could move without leaving its own interface unconstrained. LLR-164 states today's behaviour: the entry point resolves tools once and passes them to each location. |
| The run record had no internal producers, though every component writes to it. | New internal **IF-052 Record entry** (owner CMP-006; requestors the writing components). LLR-097 (every refusal states what was found and what to do) now constrains it. Notification joins IF-009's consumers (it reads the record for the message body). | A row may not list both consumers and requestors, so the writing side is its own interface. |
| Two consumer lists were incomplete. | The container requests IF-002 (the same launch request); the launch requests IF-004 (the admitted settings); notification consumes IF-003 (the run's value); the guard consumes IF-014 and IF-015 (its reclaim reads and republishes records and evidence). | Each surfaced as a flow message with no interface behind it. |
| Flows had the launch take the claim, the views triggered by publication, and flow 4's staging labelled as the store format. | The operation component takes and releases the claim (flows 2, 7, 8); the launch triggers the views; flow 4's staging participant is the guard (CMP-012); data handoffs cite the interface they travel on. | Each flow step on the component that does the work. |

After the changes, the checker reports: no empty leaf, no interface without a
consumer or a constraint, no message between components without an interface
between them, every SR in a flow or declared flow-free, and every cited id
present. The 55 placement disagreements left (groups A, B and C) are
ai-template's placement rule, not this design (see
[r3s-readiness-check.md](r3s-readiness-check.md)).

**Reading them.** At the top level, the launch (002) talks to the backup engine
only through IF-048, and the backup engine to the restore kit only through the
claim test (IF-032). The store format (016) feeds both sides with the same
seven interfaces: it is the one shared definition, by design. The run record
(006) is fed by nearly every component through IF-052, as a logging service
should be. Release guidance (024) and the container (023) stand at the edge:
they hand things to the outside, not to other components.

## The sibling argument (Parnas goal g) and the descend test

For each component, the decision it hides (its secret). Siblings must not
overlap, and together they must cover the parent.

**Top level (children of CMP-001).**

| Component | Its secret | Overlap or gap found |
|---|---|---|
| 002 Operation launch and outcome | The launch request's grammar, the dispatch per location, the fold of values, the never-prompt rule. | None. |
| 003 Configuration | The settings catalogue, the document forms and versions, the location-overlap rules. | None. |
| 004 Provisioning | How the runtime and tools are found and obtained. | None. |
| 005 Notification | The relay protocol and how the credential is used. | None. |
| 006 Run record and progress | The record's grammar, where records live, the progress cadence. | None. |
| 007 Backup engine | (A parent: everything a restore never needs.) | See below. |
| 016 Store format | The on-disk layout, the record grammar, the evidence, object naming, the digest's text, **and** free-space and volume measurement. | **Possible overlap:** volume measurement is a host-facing service, not a store-format decision. It sits here because the restore kit needs it too and the code puts it in the restore-safe module. Kept; flagged for review. |
| 017 Restore kit | (A parent: what travels in every state.) | See below. |
| 023 Container | The image, its user, mounts and action words. | None. |
| 024 Release guidance | The quick start, the configuration helper and the published description. | None. |

Coverage: every SR reaches an LLR, and every LLR's work appears on some
component's lifeline or is a static rule. Nothing the system does lacks a home.

**Backup engine (children of CMP-007).**

| Component | Its secret | Overlap or gap found |
|---|---|---|
| 009 Source scan and change detection | The walk rules (links, names, retries) and how change is judged (the comparison, the re-read schedule, the change-detection record's location). | Two decisions in one component, by the Owner's Call 1. Kept. |
| 011 Content storage and state publication | How content is stored once (the content-group owner, the compression decision, object naming) and how a state is published safely (the staging order, the collapse, the run state). | **The largest leaf** (two decisions, by the Owner's Call 2). The descend test would split it at the content map; kept by the Owner's ruling, flagged in case the code mapping shows it too large. |
| 012 Exclusive-use guard | The operating-system claim, the owner record's liveness, the staging layout, the reclaim protocol. | **Three secrets that change together.** The claim, liveness and reclaim are one protocol (rulings P-14 to P-16 moved all three at once), so a split would cut one shared definition, the failure pattern the method warns of. Kept; flagged. |
| 013 Removal and saved-state report | Re-home planning and the content-location index. | **The index is a shared service** (the check and the collapse also read it, through IF-043). Kept with removal, its main user; a Parnas shared-services component is the alternative. Flagged. |
| 014 Check, repair and kit refresh | The finding classes, what repair may correct, where kits go. | Kit placement also happens in publication (each run places the latest kit). Both follow the kit's form (IF-019); neither defines it. No overlap of secrets. |
| 015 Views | The views' forms and when to rebuild them. | None. |

**Restore kit (children of CMP-017).** Entry restoration (019: finding,
producing and verifying each entry) and outcome and report (021: classifying
the value and writing the report). Launch, admission and finishing are states
of the restore kit itself (Call 4). No overlap; together with the kit's own
states they cover SR-145, SR-010, SR-056 and SR-040.

**The descend test on the leaves.** No leaf has a describable state of its own
that the flows do not already show, and none hides a decision a stakeholder
could state that no other component owns. The three candidates (011, 012, 016)
are each kept for the reason given above. The tree stops here.
