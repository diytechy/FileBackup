## 1. Stakeholder needs met (acceptance)

- [ ] **SN-001** — Run against a known tree; every source file appears in the backup's `MANIFEST.csv`; re-running picks up new/changed files. (SN-001)
- [ ] **SN-002** — Two files with identical bytes produce one physical data file; the second is recorded as a duplicate pointing at the same data. (SN-002)
- [ ] **SN-003** — With compression on, a `.docx`/`.txt` is stored as `.7z`; a `.jpg`/`.mp4` is stored as-is. (SN-003)
- [ ] **SN-004** — After several runs, each earlier backup has a snapshot named by that backup's date; restoring one reproduces that exact state (changed files at their old content), and the latest run needs no snapshot because the live backup already is the latest state. (SN-004)
- [ ] **SN-005** — Copy a backup folder to a machine without this repo, run its restore kit, and byte-compare the result to the original — identical. (SN-005)
- [ ] **SN-006** — Running the restore kit inside a specific dated snapshot folder rebuilds exactly that earlier state, byte-for-byte; running it from the backup root rebuilds the latest state. (SN-006)
- [ ] **SN-007** — Setting `HashRecalcFreq` to `D`/`W`/`N` etc. changes whether an unchanged file is re-hashed on a given run, deterministically. (SN-007)
- [ ] **SN-008** — Toggling `PreserveFolderTree` changes the stored layout; switching an existing backup migrates its data without loss. (SN-008)
- [ ] **SN-009** — A config with multiple `BackupSets` processes each independently in one invocation. (SN-009)
- [ ] **SN-010** — With SMTP configured, a success/failure email arrives; with it omitted or `-NoMail`, none is sent. (SN-010)
- [ ] **SN-011** — A scheduled `pwsh` run completes without prompting and returns exit 0 on success, non-zero if any set failed. (SN-011)
- [ ] **SN-012** — README + `CredSetEx.ps1` let a new user build a config and run a first backup; required deps install on first use. (SN-012)
- [ ] **SN-022** — Copy a backup folder to a stock Linux box (bash, coreutils, xxhsum, 7z), run `reconstruct.sh`, and byte-compare: identical tree, from the backup root (latest) or any dated snapshot (that point in time); failures exit non-zero. (SN-022)
- [ ] **SN-023** — A backup made by the bash engine restores byte-exact via either restorer, and vice versa; dedup/snapshot semantics match the shared contract. (SN-023)
- [ ] **SN-024** — One checked-in command builds the image and proves a compressed byte-exact roundtrip; the image can be exported/imported as a tar or pushed/pulled through a Docker-compatible registry. (SN-024)
- [ ] **SN-026** — Both restorers return the same documented exit code per failure class; deliberately induced instances of each class (clean, content missing, host/dependency problem, bad invocation/precondition, damaged index) each return their own code, identical on Windows and Linux. (SN-026)
- [ ] **SN-028** — CI builds, exports, `docker load`s, and re-smoke-tests the image; CI publishes/pulls through a throwaway registry and re-smoke-tests the pulled image; the container smoke test runs a second, source-mutating pass and restores both the latest state and the superseded snapshot in-container, byte-comparing each against the correct source generation. (SN-028)
- [ ] **SN-029** — Asking the tool to remove a named snapshot leaves every remaining dated state — and the latest state — restorable byte-exact in all four storage modes, including when the removed folder held the only copy of shared content; a dry run first reports the same reclaim figure the real removal achieves; anything that would lose content is refused before a single byte is touched, with a distinct exit status; a run interrupted at any point loses nothing and can simply be run again. (SN-029)
- [ ] **SN-030** — An on-demand check reports every place the stored form and the index disagree, across the live backup and every snapshot, without changing anything, and a repair mode fixes the ones that are unambiguously wrong; restoring any state after a compression-policy change reproduces the original bytes exactly, or fails loudly, but never writes archive bytes under a real filename; a backup run that would not fit refuses before writing anything. (SN-030)
- [ ] **SN-031** — After a data file inside the backup root is externally deleted: the next backup run exits 0 having re-pointed or re-copied the row from the still-matching source, and the restored tree is byte-exact; a new source file with identical content never adopts a row whose DataPath is blank; `-Action Verify` reports every row whose bytes are gone from the pool entirely, with a distinct finding class and non-zero exit, instead of reporting the store clean. (SN-031)
- [ ] **SN-032** — A source file whose name is invalid on either platform is skipped with one ERROR naming the file and the offending character, the set fails (non-zero exit), everything else in the set is still backed up, and no manifest row is written for the skipped file. (SN-032)
- [ ] **SN-033** — A store whose data file has been altered (wrong payload, bit-flip, or truncation) restores byte-exact from a surviving pool copy, or fails non-zero naming the row — never exit 0 with wrong bytes. (SN-033)
- [ ] **SN-034** — After editing one of two identical files, restoring the previous snapshot still reproduces the old bytes for **both** paths, and the pool audit reports no blank row whose content is unaccounted for; no data file's bytes ever change while a live manifest row claims them. (SN-034)
- [ ] **SN-013** — Interruption / power loss / killed mid-operation (SN-013)
- [ ] **SN-014** — Invalid input — config file missing (SN-014)
- [ ] **SN-015** — Missing **required** dependency / wrong runtime (PowerShell 5.1, no `System.IO.Hashing`) (SN-015)
- [ ] **SN-016** — Missing external tool (7-Zip when compression is selected, ffprobe for media metrics) (SN-016)
- [ ] **SN-017** — Awkward file names (Unicode, `[brackets]`, `(parens)`, spaces) (SN-017)
- [ ] **SN-018** — A *nested* user file happens to be named like infrastructure (e.g. `MANIFEST.csv`) (SN-018)
- [ ] **SN-019** — Restore target too small / unwritable (SN-019)
- [ ] **SN-020** — Email/SMTP failure during notification (SN-020)
- [ ] **SN-021** — A run with nothing changed (idempotent re-run) (SN-021)
